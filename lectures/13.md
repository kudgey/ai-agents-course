Три інструменти описати легко. Коли їх тридцять і вони живуть у різних сервісах, потрібен спільний протокол. Лекція йде від арифметики інтеграцій через архітектуру MCP до A2A і до інцидентів, які показали ціну довіри.

## Чого ви навчитеся

Після цієї лекції ви зможете:

1. Порахувати виграш протоколу для конкретного числа застосунків і систем.
2. Назвати три ролі MCP і три примітиви та сказати, хто ініціює кожен.
3. Обрати транспорт між stdio і Streamable HTTP за місцем розгортання сервера.
4. Провести межу між MCP і A2A за тим, що з чим з'єднується.
5. Скласти таблицю «ризик — контрзахід — залишковий ризик» для підключення сервера.

## Арифметика, заради якої існує протокол

Доки кожен застосунок пише власний конектор до кожної системи, кількість інтеграцій росте як **добуток** двох чисел. Спільний протокол розриває добуток на **суму**.

$$I_{\text{прямі}} = M \cdot N, \qquad I_{\text{через протокол}} = M + N$$

| Позначення | Значення |
|---|---|
| $M$ | застосунків, яким потрібні дані |
| $N$ | систем і джерел даних |
| $I$ | інтеграцій, які хтось пише і супроводжує |

Для факультету з чотирма застосунками і сімома системами це 28 конекторів проти 11; на десяти застосунках і двадцяти джерелах — 200 проти 30. Виграш з'являється не одразу: на малих числах суми й добутки майже збігаються, і накладні витрати протоколу помітніші за економію.

## Що саме стандартизує протокол

MCP описує себе як відкритий протокол інтеграції LLM-застосунків із зовнішніми джерелами даних та інструментами. Аналогію специфікація називає сама:

> *MCP takes some inspiration from the Language Server Protocol, which standardizes how to add support for programming languages across a whole ecosystem of development tools.*

<Compare :head="['Що фіксує протокол', 'Що лишається вашим', '', '', '']" :items="[{k: 'виявлення можливостей', v: 'які інструменти взагалі давати'}, {k: 'опис входу схемою', v: 'семантика полів і валідація'}, {k: 'формат виклику і відповіді', v: 'реалізація і права доступу'}, {k: 'два класи помилок', v: 'політика повтору і зупинки'}]" />

Протокол фіксує форму розмови і **не робить роботу за вас**: він не вирішує, які саме дані відкривати і з якими правами.

## Три ролі дослівно зі специфікації

Специфікація формулює архітектуру одним реченням: *«Hosts: LLM applications that initiate connections; Clients: Connectors within the host application; Servers: Services that provide context and capabilities.»*

<Cards :items="[{k: 'Хост', v: 'застосунок, що ініціює зв\'язок', extra: 'сервіс асистента'}, {k: 'Клієнт', v: 'конектор усередині хоста', extra: 'один на кожен сервер'}, {k: 'Сервер', v: 'служба з контекстом і діями', extra: 'сервер над розкладом'}]" accent="accent" :numbered="false" />

Найчастіше плутають хост із клієнтом. Сервер може працювати на тій самій машині або в чужому дата-центрі, і протокол виглядає однаково. Різниця в тому, **з якими правами він виконується**.

## Три примітиви і хто ними керує

Сервер пропонує клієнтові три речі, і розрізняються вони не форматом, а тим, хто вирішує момент використання. Уточнення специфікації варте того, щоб прочитати вголос: *«This refers to who decides when the prompt is used, not who authors its content.»*

<Cards :items="[{k: '<code>tools</code>', v: 'модель', extra: 'інструмент зі схемою входу'}, {k: '<code>resources</code>', v: 'застосунок', extra: 'дані, що їх кладе хост'}, {k: '<code>prompts</code>', v: 'користувач', extra: 'шаблон, обраний людиною'}]" accent="accent" :numbered="false" />

Методи парні: `tools/list` і `tools/call`, `resources/list` і `resources/read`, `prompts/list` і `prompts/get`. Інструмент із лекції 12 переїжджає в MCP майже без змін, бо його схема входу і типізована помилка вже описані так, як цього вимагає протокол.

## Два транспорти і їхні правила

| Аспект | stdio | Streamable HTTP |
|---|---|---|
| Канал | stdin/stdout процесу | один MCP-endpoint |
| Фреймінг | рядок без переносів | один POST на повідомлення |
| Відповідь | рядок у stdout | JSON або потік SSE |
| Нотифікація | — | `202 Accepted` без тіла |
| Скасування | `notifications/cancelled` | закриття потоку SSE |
| Заголовки | немає | `MCP-Protocol-Version`, `Mcp-Method` |
| Безпека | межа процесу | перевірка `Origin`, лише localhost |

stdio доречний, коли сервер запускається як дочірній процес на машині користувача. Streamable HTTP — коли один сервер обслуговує багатьох. Найчастіший практичний баг stdio-сервера банальний: `print()` у коді ламає протокол, бо сервер «MUST NOT write anything to its `stdout` that is not a valid MCP message» — для логів є `stderr`.

## MCP-сервер у двадцять рядків

Той самий `get_schedule` із лекції 12, тепер як MCP-сервер через [офіційний Python SDK](https://github.com/modelcontextprotocol/python-sdk):

```python
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("faculty-data")          # ім'я сервера, яке побачить хост

@mcp.tool()
def get_schedule(course: str, kind: str) -> dict:
    """Повертає розклад за назвою курсу.

    Використовуй для питань про час, день або аудиторію.
    НЕ використовуй для питань про правила чи накази — для них є search_docs.

    Args:
        course: назва курсу, напр. «Бази даних»
        kind: один із lecture, lab, consult
    """
    rows = db.query(course=course, kind=kind)
    if not rows:
        raise ValueError(f"За курсом «{course}» ({kind}) записів немає.")  # → isError
    return rows[0]

if __name__ == "__main__":
    mcp.run(transport="stdio")         # логи — тільки в stderr!
```

Схема входу генерується з анотацій типів, а докстрока стає описом, який читає модель. Виняток перетворюється на результат з `isError: true` — тобто в дані для моделі, а не в падіння протоколу.

## Ревізія має форму дати

Версія MCP записується як `YYYY-MM-DD` і позначає «the last date backwards incompatible changes were made». Сумісні зміни номер не піднімають, тому дата в конфігурації клієнта — це **межа сумісності**, а не дата релізу.

## Форма повідомлення JSON-RPC

Запит містить поля `jsonrpc`, `id`, `method` і `params`; відповідь — або `result`, або `error` з тим самим `id`. З ревізії `2026-07-28` кожен результат має обов'язкове поле `resultType` зі значенням `complete` або `input_required`.

## Сесії більше немає

Найбільша зміна останньої ревізії стосується не примітивів, а того, чи пам'ятає сервер, з ким він говорить. Відповідь тепер від'ємна, і це зроблено навмисно: будь-який POST можна віддати будь-якому інстансу за балансувальником.

<Cards :items="[{k: 'стан не живе у транспорті', v: 'видавати handle і передавати аргументом'}, {k: 'обрив потоку губить запит', v: 'повторювати з новим <code>id</code>'}, {k: 'повтор дублює побічну дію', v: 'ідемпотентність на боці сервера'}]" accent="accent" :numbered="false" />

Резюмованість SSE прибрана: *«A broken response stream loses the in-flight request; clients MUST re-issue it as a new request with a new request ID.»* Для довгого інструмента це означає, що **ідемпотентність стає вимогою**, а не гарною практикою.

| Прибрано `ping` і `logging/setLevel` | 2575 |

MRTR означає, що сервер більше не ініціює запитів: він повертає результат із `resultType: "input_required"`, а клієнт повторює ту саму операцію, доклавши `inputResponses`. Потік запитів став односпрямованим. Хто будував агента на серверному sampling, має дванадцять місяців на перехід.

## Кеш переліку інструментів

Перелік із двадцяти інструментів не тягнеться в кожен запит: клієнт бере його з кешу, доки не спливе `ttlMs`.

Через це **зміна набору інструментів на сервері доходить до агента із затримкою**, і це треба закладати в розгортання. Ще одна пастка іменування: `structuredContent` у результаті сервера «is unrelated to LLM structured outputs», тобто до обмеженого декодування з лекції 05 стосунку не має.

## A2A: агент як непрозорий співрозмовник

A2A визначає себе як «an open standard designed to facilitate communication and interoperability between independent, potentially opaque AI agent systems». Принцип непрозорого виконання: *«Agents collaborate effectively without exposing their internal logic, memory, or proprietary tools.»*

<Cards :items="[{k: '<code>provider</code>', v: 'хто відповідає за агента'}, {k: '<code>capabilities</code>', v: 'стрімінг, push, розширена картка'}, {k: '<code>skills</code>', v: 'що агент уміє, з прикладами'}, {k: '<code>interfaces</code>', v: 'транспорти й адреси'}, {k: '<code>securitySchemes</code>', v: 'як автентифікуватись'}, {k: '<code>signature</code>', v: 'підпис картки'}]" accent="accent" :numbered="false" />

Точка входу — Agent Card за адресою `/.well-known/agent-card.json`. Публічна картка зручна для інтеграції та водночас є описом вашої внутрішньої архітектури для будь-кого.

## Життєвий цикл задачі A2A

Одиниця роботи в A2A — задача з унікальним ідентифікатором, а не окремий виклик. Головне правило стосується кінця: *«Once a task reaches a terminal state, it cannot restart.»*

<Cards :items="[{k: 'Активні', v: '<code>submitted</code>, <code>working</code>', extra: 'виконується'}, {k: 'Перервані', v: '<code>input-required</code>, <code>auth-required</code>', extra: 'чекає на людину або токен'}, {k: 'Термінальні', v: '<code>completed</code>, <code>failed</code>, <code>canceled</code>, <code>rejected</code>', extra: 'перезапуску немає'}]" accent="accent" :numbered="false" />

Уточнення вимагає **нової задачі** в тому самому `contextId`. Методи ядра відповідають цій моделі: `SendMessage` створює роботу, `GetTask` і `SubscribeToTask` стежать, `CancelTask` зупиняє.

## MCP і A2A: що з чим з'єднує

Правило коротке: **MCP під'єднує агента до інструментів, A2A з'єднує агентів між собою.**

## Протокол не є межею довіри

MCP-сервер — це стороння програма, яка виконується **з правами вашого процесу**. Описи й анотації інструментів приходять від сервера, потрапляють у промпт і є недовіреними даними: *«clients MUST consider tool annotations to be untrusted unless they come from trusted servers.»*

## Ризик, контрзахід, залишковий ризик

## Лабораторна 4: сервер над даними університету

Артефакт — read-only MCP-сервер над даними факультету з двома інструментами: `search_docs` над індексом і `get_schedule` над SQLite розкладу. Жодного запису: `create_ticket` у цьому сервері немає взагалі, і його відсутність є частиною умови.

## Шість питань і відповідей

<Cards :items="[{k: 'Скільки інтеграцій', v: '$M+N$ замість $M \\cdot N$'}, {k: 'Хто ініціює обмін', v: 'завжди клієнт, з <code>2026-07-28</code> без винятків'}, {k: 'Локально чи мережею', v: 'stdio для процесу, HTTP для спільного сервера'}, {k: 'Агент до інструментів', v: 'MCP'}, {k: 'Агент до агента', v: 'A2A'}, {k: 'Де межа довіри', v: 'у вашому процесі, не в протоколі'}]" accent="accent" :numbered="false" />

Перші три рядки стосуються проєктування, останній — експлуатації, і саме він найчастіше лишається без власника. Протокол дає спільну мову; права і наслідки лишаються вашими.

## Межі лекції

Обидва протоколи молоді, і їхні ревізії змінюються швидше за семестр: за півтора року MCP замінив транспорт, прибрав сесії та відправив у відставку Sampling, Roots і Logging. Тому в курсі ви вчите межі й контракти, а не синтаксис конкретної версії.

Накладні витрати самого MCP на затримку публічно не виміряні, тому порівняння з прямим викликом функції ви робите на власному стенді. Протокол не описує, як перевіряти сервер перед підключенням, і не дає механізму контролю доступу — це відповідальність хоста. A2A працює з непрозорими агентами, тому зневадити чужого агента ви не зможете взагалі.

## Висновки

Протокол замінює добуток на суму: замість $M \cdot N$ приватних конекторів пишуться $M$ клієнтів і $N$ серверів, і на десяти застосунках із двадцятьма джерелами це 30 інтеграцій замість 200.

MCP описує три ролі та три примітиви, які розрізняються тим, хто вирішує момент виклику. Ревізія `2026-07-28` зробила протокол stateless, а ціною стали явні handle та ідемпотентність. MCP під'єднує агента до інструментів, A2A з'єднує агентів між собою і працює задачами з незворотними термінальними станами. Підключення сервера є **розширенням межі довіри**, а не інтеграцією.
