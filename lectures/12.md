## Чого ви навчитеся

Після цієї лекції ви зможете:

1. Оголосити інструмент шістьма полями і сказати, які три з них модель не бачить.
2. Описати п'ять кроків обміну між застосунком і моделлю.
3. Пояснити, що саме додає ReAct і чого він не додає.
4. Написати повідомлення про помилку, з якого випливає наступна дія.
5. Побудувати таблицю прав інструментів із колонкою зворотності.

## Шість полів одного оголошення

Оголошення інструмента фіксує домовленість між моделлю, застосунком і системою, до якої йде виклик. Перші три поля потрапляють у запит до моделі, останні три живуть у вашому реєстрі й перевіряються **до** виконання.

| Поле | Що фіксує |
|---|---|
| Назва | стабільний ідентифікатор виклику |
| Призначення | коли інструмент доречний |
| Схема аргументів | типи й обов'язкові поля |
| Схема результату | що повертає застосунок |
| Побічні ефекти | читає чи змінює стан |
| Права | від чийого імені виконується |

Модель не бачить трьох останніх рядків взагалі. Саме тому рішення «цей виклик змінює стан, отже потрібна людина» ухвалює **код**, а не текст відповіді.

## Опис інструмента читає модель

Опис інструмента є частиною промпта. Документація Anthropic формулює це прямо: модель викликає інструмент тоді, коли запит відповідає описаній у ньому здатності, а відповіді ще немає в контексті.

Звідси два практичні наслідки. Два інструменти з майже однаковими описами дають хиткий вибір між ними, і жодне налаштування температури цього не лікує. Опис без умов застосування дає виклики там, де відповідь уже лежить у контексті, і кожен такий виклик коштує затримки та токенів.

Опис пишеться під читача-модель: одне речення про призначення, окремо про те, **коли інструмент недоречний**, і приклад аргументів у полі опису кожного параметра.

## Три діалекти, одне ядро

Спільне ядро всюди однакове: ім'я, опис природною мовою і JSON Schema типу `object` зі списком `required`. Розбіжність зводиться до назви поля зі схемою.

| Діалект | Поле схеми | Особливість |
|---|---|---|
| Anthropic | `input_schema` | strict tool use |
| OpenAI | `parameters` | `strict: true` |
| MCP | `inputSchema` | додає `title` |

Строгий режим вимагає `additionalProperties: false` для кожного об'єкта і всі властивості в масиві `required`. Гарантія при цьому синтаксична: схема гарантує, що поле `date` існує і є рядком, але не те, що дата правильна. **Семантику аргументів перевіряє сам інструмент**, і ніхто інший цього за нього не зробить.

## Оголошення інструмента в коді

Три інструменти асистента навчального відділу. Опис написаний під читача-модель — з умовами, коли інструмент недоречний:

```python
TOOLS = [
    {
        "name": "get_schedule",
        "description": (
            "Повертає розклад занять і консультацій за назвою курсу. "
            "Використовуй, коли питання про час, день або аудиторію. "
            "НЕ використовуй для питань про правила, накази чи перескладання — "
            "для них є search_docs."
        ),
        "input_schema": {
            "type": "object",
            "properties": {
                "course": {"type": "string", "description": "назва курсу, напр. «Бази даних»"},
                "kind": {"type": "string", "enum": ["lecture", "lab", "consult"]},
            },
            "required": ["course", "kind"],
            "additionalProperties": False,          # вимога strict-режиму
        },
        "strict": True,                             # ← вмикає гарантію форми аргументів
    },
    # search_docs — read-only індекс; create_ticket — запис, потребує людини
]

r = client.messages.create(model="claude-sonnet-4-5", max_tokens=1024,
                           tools=TOOLS, messages=messages)
print(r.stop_reason)     # 'tool_use'
```

Рядок «НЕ використовуй для…» коштує двадцять токенів і знімає більшість хибних викликів.

## Один виклик, п'ять кроків обміну

Найпоширеніша хибна модель у голові студента: нібито модель виконує функцію. **Вона її лише просить.**

1. Запит іде до моделі разом із переліком інструментів.
2. Модель повертає виклик з аргументами: `stop_reason: "tool_use"` і блок `tool_use` у Anthropic, масив `tool_calls` у OpenAI.
3. Ваш код виконує операцію.
4. Результат повертається тим самим ідентифікатором: `tool_result` з тим самим `tool_use_id`.
5. Модель продовжує та або відповідає, або просить наступний виклик.

Модель у цьому обміні не має доступу ні до мережі, ні до диска: вона повертає текст, який ваш код погодився інтерпретувати як прохання.

## Режими tool_choice

Вибір інструмента можна віддати моделі, а можна відібрати. Обидва діалекти дають той самий набір режимів під різними іменами.

| Режим | Anthropic | OpenAI |
|---|---|---|
| Авто, типово | `{"type":"auto"}` | `"auto"` |
| Будь-який | `{"type":"any"}` | `"required"` |
| Конкретний | `{"type":"tool"}` | `{"type":"function"}` |
| Заборонено | `{"type":"none"}` | `"none"` |
| Підмножина | немає | `allowed_tools` |

Режим `any` змушує зробити щонайменше один виклик, але **не робить його доречним**: під примусом модель викличе хоч щось навіть тоді, коли правильна дія була б відповісти напряму. Примус доречний у вузлі, де ви вже знаєте, що дія потрібна.

## Паралельні виклики і межа набору

Обидва провайдери дозволяють кілька викликів в одній відповіді й дають прапорець, щоб це вимкнути: `disable_parallel_tool_use` у Anthropic, `parallel_tool_calls: false` у OpenAI.

Паралельність безпечна **лише тоді, коли виклики незалежні**. Два виклики в одній відповіді формуються без знання один про одного, тому будь-яка залежність за даними ламається, а два записи можуть застосуватися в непередбаченому порядку.

Окремо про розмір набору: документація радить тримати початково доступних функцій менше двадцяти саме заради точності вибору, а для великих наборів використовувати простори імен в іменах. Як віддавати десятки інструментів без десятків інтеграцій — лекція 13.

## ReAct дослівно

Формулювання авторів роботи 2022 року просте:

> *We augment the agent's action space to $\hat{A} = A \cup L$, where $L$ is the space of language.*

> *A thought $\hat{a}_t$ in the language space … does not affect the external environment, thus leading to no observation feedback.*

Простір дій розширюється мовою; думка нічого не змінює в середовищі, а отже не дає спостереження у відповідь. Практично це чергування трьох елементів: думка формулює, чого бракує; дія викликає інструмент; спостереження повертає результат у контекст. Думка коштує токенів і затримки, а платить за себе тим, що наступна дія стає обґрунтованою.

## Розширений простір дій

Політика тут — це модель із few-shot промптом, а не навчена мережа. На кожному кроці вона обирає з об'єднаного простору, а контекст росте на кожну дію разом з її спостереженням.

$$\hat{A} = A \cup L, \qquad \hat{a}_t \sim \pi(\hat{a}_t \mid c_t), \qquad c_{t+1} = (c_t, \hat{a}_t, o_{t+1})$$

| Позначення | Значення |
|---|---|
| $A$ | дії, що змінюють середовище |
| $L$ | простір мови, тобто думки |
| $\hat{a}_t$ | дія або думка на кроці $t$ |
| $o_t$ | спостереження, відповідь інструмента |
| $c_t$ | контекст, уся історія до кроку $t$ |

Для думки спостереження відсутнє, тому оновлення контексту вироджується. Звідси й головний компроміс циклу: кожна думка займає місце у вікні і не наближає до результату сама по собі.

## HotpotQA і FEVER на PaLM-540B

Роботу 2022 року цитують частіше, ніж читають. Її власні таблиці кажуть обережніше, ніж переказ. Умови однакові для всіх рядків: PaLM-540B, few-shot промптинг, greedy decoding.

| Метод | HotpotQA, EM % | FEVER, Acc % |
|---|---|---|
| Пряма відповідь | 28.7 | 57.1 |
| CoT | 29.4 | 56.3 |
| CoT-SC, 21 семпл | 33.4 | 60.4 |
| Act, лише дії | 25.7 | 58.9 |
| ReAct | 27.4 | 60.9 |
| CoT-SC → ReAct | 34.2 | 64.6 |
| ReAct → CoT-SC | 35.1 | 62.0 |
| Навчений SoTA 2022 | 67.5 | 89.5 |

Чесна нота: на HotpotQA сам ReAct дає 27.4 і **програє** і CoT, і прямій відповіді. Виграш з'являється лише в комбінації з self-consistency. На FEVER картина інша: ReAct вищий за CoT на 4.6 пункти. Джерело — [ReAct](https://arxiv.org/abs/2210.03629).

| Задача | Бейзлайн | ReAct | Метрика |

Запит: «Коли консультація з бази даних і чи можу я перескласти».

| Крок | Зміст | Токенів |
|---|---|---|
| Thought | потрібен розклад консультацій | 18 |
| Action | `get_schedule(course="БД", kind="consult")` | 24 |
| Observation | `{"day":"четвер","time":"14:30","room":"305-18"}` | 31 |

## Дві породи помилок інструмента

Специфікація MCP розділяє їх явно, і це розділення варте того, щоб перенести його у власний код навіть без MCP.

| Ознака | Протокольна | Виконання |
|---|---|---|
| Що це | зламаний запит | збій усередині інструмента |
| Приклад | невідомий інструмент | відмова API, невалідний вхід |
| Форма | код помилки JSON-RPC | результат з `isError: true` |
| Кому корисно | застосунку | моделі |

Помилки виконання специфікація описує як «actionable feedback that language models can use to self-correct and retry with adjusted parameters». Протокольні помилки моделі зазвичай не допомагають: із «невідомий інструмент» вона не виведе правильної наступної дії.

## Клас помилки, повідомлення, реакція

Повідомлення пишеться так, щоб з нього випливала наступна дія. Внутрішні шляхи, назви таблиць і трасування стека в контекст **не потрапляють**.

| Клас | Повідомлення моделі | Очікувана реакція |
|---|---|---|
| Невалідний аргумент | яке поле, який формат | виправити аргумент |
| Не знайдено | що саме не знайдено | інший запит |
| Немає прав | дія заборонена | ескалація людині |
| Ліміт швидкості | повтор через 30 с | пауза або обхід |
| Збій сервісу | тимчасовий збій | повтор із відкатом |
| Порожній результат | 0 записів за фільтром | послабити фільтр |

Порожній результат навмисно виділено окремо від збою. Це **успішний** виклик, і модель має поводитися з ним інакше, ніж із відмовою сервісу.

## Типізовані помилки в коді

Інструмент, що падає стек-трейсом у контекст, забирає крок і нічого не дає. Помилка має бути придатною до дії:

```python
class ToolError(Exception):
    def __init__(self, kind: str, message: str, retryable: bool):
        self.kind, self.message, self.retryable = kind, message, retryable

def get_schedule(course: str, kind: str) -> dict:
    rows = db.query(course=course, kind=kind)
    if not rows:                                        # успішний виклик, порожній результат
        raise ToolError("empty", f"За курсом «{course}» ({kind}) записів немає. "
                                 f"Доступні види: lecture, lab, consult.", retryable=False)
    return rows[0]

def dispatch(name: str, args: dict) -> dict:
    try:
        return {"ok": True, "data": REGISTRY[name](**args)}
    except ToolError as e:
        return {"ok": False, "error": e.kind, "message": e.message}   # ← йде в контекст
    except Exception:
        log.exception("tool %s failed", name)                          # стек-трейс — у лог,
        return {"ok": False, "error": "service",                       #   а не моделі
                "message": "Тимчасовий збій сервісу. Спробуй ще раз пізніше."}
```

Модель бачить `message`, і з нього випливає наступна дія. Стек-трейс бачить лише інженер.

## Повтор, ідемпотентність і бюджет

Повторний виклик безпечний для читання і небезпечний для запису. Ані Messages API, ані документація OpenAI не описують ключа ідемпотентності, тому дедуплікація будується на вашому боці.

| Подія | Дія системи |
|---|---|
| Повтор читання | виконати ще раз |
| Повтор запису | ключ дедуплікації |
| Восьмий виклик | зупинити і підсумувати |
| 60 секунд | віддати часткове й вийти |

Повтор із вербальним розбором невдачі, як у [Reflexion](https://arxiv.org/abs/2303.11366), покращує результат нерівномірно: на HumanEval pass@1 зростає з 80.1 до 91.0, на ALFWorld з ≈73 % до 97 %, але на MBPP дає 77.1 проти 80.1, тобто **регресію**.

## Інструмент, права, зворотність, людина

Таблиця прав будується для кожного інструмента **до** першого запуску агента. Колонка зворотності важливіша за колонку прав: вона каже, чи можна відкотити наслідок помилки.

| Інструмент | Права | Зворотна | Людина |
|---|---|---|---|
| `search_docs` | read-only індекс | так | ні |
| `get_schedule` | read-only SQLite | так | ні |
| `create_ticket` | запис у деканат | ні | так |
| `send_email` | вихідна пошта | ні | так |
| `run_python` | пісочниця без мережі | так | ні |

Незворотна дія з правом запису завжди отримує людину в контурі. Пісочниця без мережі робить виконання коду зворотним, бо єдиний наслідок падіння — це втрачений контейнер.

## Найменші привілеї на практиці

OWASP називає три корені надмірних повноважень: зайва функціональність, зайві права і зайва автономія. Кожен закривається окремо.

Набір інструментів звужується до потрібних задачі. Аргументи проходять allowlist на боці інструмента. Читання йде під обліковими даними лише для читання. Виконання коду живе в окремому контейнері без облікових даних і з обмеженим вихідним трафіком.

**Авторизація перевіряється в системі, до якої йде виклик, а не в промпті:** рішення на боці моделі не є рішенням про доступ. Аудит-лог пише кожен виклик з аргументами, результатом і рішенням про підтвердження.

## Чотири способи втратити контроль

Ці відмови трапляються не через слабку модель, а через відсутній запобіжник у циклі.

| Відмова | Ознака в логу | Запобіжник |
|---|---|---|
| Нескінченний цикл | той самий виклик поспіль | лічильник кроків |
| Вигадані аргументи | схема ок, сенсу немає | валідація в інструменті |
| Запис без підтвердження | стан змінено без людини | підтвердження в графі |
| Дані як інструкція | текст із наказом у результаті | межа довіри |

Ручний розбір 200 траєкторій показав, чим ReAct платить за заземленість: галюцинацій фактів у нього 0 % проти 56 % у CoT, зате 47 % його помилок — це помилки міркування, значна частина яких зводиться до повторення того самого пошуку.

## Що робить лабораторна 3

Артефакт лабораторної — агент асистента з трьома інструментами: `search_docs`, `get_schedule` і `create_ticket`.

| Частина | Вимога |
|---|---|
| Оголошення | JSON-схема з описом призначення |
| Помилки | типізовані, з класу таблиці |
| Цикл | ReAct явно, лог думки/дії/спостереження |
| Бюджет | 8 викликів і 60 секунд |
| Запис | підтвердження людини на рівні коду |
| Здається | лог із десяти прогонів |

У логу має бути видно принаймні один вичерпаний бюджет і принаймні одну відпрацьовану типізовану помилку. Оцінюється не краса відповіді, а те, чи кожен виклик має права, межу і слід у логу.

## Шість рішень цієї лекції

| Питання | Що фіксуємо |
|---|---|
| Що модель бачить | назву, опис, схему аргументів |
| Хто виконує виклик | застосунок, ніколи не модель |
| Чим керуємо вибором | опис і режим `tool_choice` |
| Що дає ReAct | заземленість, не точність |
| Що робить помилка | веде до наступної дії |
| Що стримує агента | права, зворотність, бюджет |

Права й бюджет належать **коду**. Опис і думки належать **промпту**. Плутанина між цими двома колонками і є типовою причиною того, що агент робить не те, а виправляють його не там.

## Межі лекції

| Метод | Чого не вміє |
|---|---|
| Строга схема | гарантує форму, не сенс |
| Великий набір | точність падає після двадцяти |
| ReAct | не підвищує точність QA сам |
| ReAct | короткозорий, залежить від пошуку |
| Toolformer | інструменти фіксовані навчанням |
| Пісочниця | не рятує від дозволеного запису |

ReAct у малих моделях без донавчання працює погано: авторам знадобилося близько трьох тисяч траєкторій, щоб довчити PaLM-8B і PaLM-62B. Публічних чисел про частоту зациклень у продакшені немає взагалі.

## Висновки

Оголошення інструмента є контрактом і водночас промптом: модель обирає за описом, а виконує ваш код за схемою і правами. Строгий режим гарантує синтаксис аргументів, а не їхній сенс.

ReAct додає до простору дій думки й міняє розподіл помилок: галюцинації фактів зникають, натомість з'являються цикли й порожні пошуки, і виграш у точності залежить від задачі. Типізована помилка коштує одного кроку і повертає агента на маршрут, а стек-трейс коштує того самого кроку і не повертає нічого. Контроль дає не промпт, а права, зворотність дії та бюджет кроків, які перевіряються поза моделлю.
